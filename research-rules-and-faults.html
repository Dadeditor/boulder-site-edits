Rules declared once.
A graph that can find a fault.

Four hand-kept descriptions of one rule drifted apart and still passed their tests. Here is what replaced them, and how we measure whether a dependency graph is worth having.

Adhitya Mohan 10 November 2026 Verification ~9 min read

Running thousands of copies of a game on a GPU is only useful if each copy is the game. If a GPU lane drifts from what Godot would have done, every test result and every trained policy built on it inherits the error. So the interesting engineering isn't the speed. It's the machinery that lets you believe the speed.

Four artifacts, one rule

A rule written directly as a kernel is one example deep. The gravity rule in our first version was exactly that: a hand-written Warp function, a hand-maintained edge table beside it, a hand-maintained map from groups to fields beside that, and a causal graph reconstructed from the map.

Four artifacts described one rule, and they drifted. The camera phase read a transform field that no declared edge covered. The write-mask bits were hardcoded against an earlier update order, so the input phase reported itself as audio and the header phase set a bit outside the valid range. Both passed their tests.

The lesson isn't "be more careful". Any fact that's written down in more than one place will eventually disagree with itself. The fix is to write it down once.

What derives from the declaration

Once reads and writes are declared, three things that used to be maintained by hand become computed:

  • The update order. An edge is same_step when one rule reads a field another rule writes in the same step, and next_step when it reads the previous step's value. A topological sort over the same-step edges gives the order, and the kernel calls one function per phase in that order.
  • The write-mask bits. The bit for a phase is its index in the shipped order. It can't go stale against an earlier order, because there's only one.
  • The causal graph. Built from the same edges.

The derivation also disagreed with the hand-written table, which is the best evidence that it was worth doing. It produced 37 edges against the hand table's 36, reproducing 34 of them and printing a reason for every difference. Three were real corrections. The input rule, for example, is a read-modify-write on linear velocity, so it reads the previous step's value and needs an incoming next-step edge. The hand table had treated input as coming from outside and declared none.

Three backends, one answer

The gravity rule, declared once, produces bit-identical results from the Warp and numpy backends over 120 ticks and four lanes, on all 25 fields the rule set touches. The GDScript backend agrees with numpy bit-identically too, not merely within a tolerance. Porting the old hand-written kernel through the new representation reproduces it bit-identically, which checks that changing the representation didn't change the arithmetic.

The representation also states its own gap. It declares 25 fields; the layout has 77. The other 52 are listed in a separate file, each with the mechanism that writes it, or the word nothing. A field that's both written by a rule and listed there is a load error, and a field in neither place is a coverage failure. That's coverage proved rather than asserted.

A graph that can find a fault

A dependency graph over the state exists for one purpose: to trace a fault from where it's introduced to where it becomes visible. A graph that can't do that is documentation.

The construction rules come from a specification written for game engines and worked through on a chemical-plant simulator. Nodes are the code's variables, grouped by what they hold. An edge means one variable is computed from another, and every edge is marked as acting within a state update or carrying into the next. The order of updates within a step is part of the graph, not a convention outside it.

The most useful structure in that worked example is its delay nodes: held samples, valve memory, controller memory, each one previous-value storage. Two of the ten documented bug classes live only there. An update-order error shows up as a downstream node lagging an upstream one by exactly one step. Order dependence shows up as two identical runs diverging from one node. A graph that collapses a delay node into its source can't express either.

That's why our layout carries previous values unconditionally. Godot marks two of its four transform variants as interpolation-only, and stores five camera parameters as interpolated properties. The kernel can't know which ones the renderer will use, so the image carries all of them and the graph gives them their own group.

Ten gates, each a mutation

The graph's value is measurable, so we measure it. Ten gates each inject one rule mutation, one per documented bug class, run the mutated world beside the reference, and assert three things: the name of the first field to diverge, a value signature, and the number of hops from the injected fault to that field.

All ten pass. This is mutation testing, not a signature the tool also defines, and that distinction is what makes the result mean something. The two-hop case uses a synthetic unrecorded impulse, which is the shape the specification describes: a fault that changes a variable nobody records, which then changes one somebody does.

What parity means

Parity is claimed against Godot's own physics, not against ourselves. Both sides run the same rule from the same initial state with the same time step, and the comparison prints both sides rather than just a difference. Every number carries the condition it holds under:

One result doesn't match, and it's stated rather than tolerated. The continuous fields agree; the contact event stream doesn't. The kernel fires 74 contact ticks to Godot's 78, and its first contact is one tick late. That latency is structural: the declared order makes contact read the previous step's transform. Declaring it same-step instead creates a three-node cycle, which the order validator rejects. It's the update-order bug class from the table above, showing up as a property of the declared order rather than as a mistake.

Precision is the other sharp edge. Against a 32-bit reference over 50 ticks and 32 lanes, bf16 gives a worst error of 0.905 on linear velocity and flips the contact flag; fp16 gives 0.157 and flips both the contact and sleeping flags. bf16 is worse here because it has eight mantissa bits to fp16's ten, and its advantage, range, is something this workload doesn't need. Both flip a contact flag, which means lower precision changes the outcome of a collision, not just its rounding.

How several of these gates were themselves wrong, and how we found out, is the subject of a separate essay.
