A gap you can close.
A wall you route around.

Our prototype has six documented limits. Five are engineering gaps that time and effort close. One is an architectural boundary that no budget moves, and the honest response to it is a different plan, not a bigger one.

The earlier essays end with what the prototype doesn't do: what stays outside the kernel, the one parity result that doesn't match, what four cards don't deliver. This piece collects those limits in one place and asks a blunter question of each: does time fix it?

Two kinds of limit

A limit is either a gap or a wall. A gap exists because nobody has done the work yet; the path is known and effort closes it. A wall exists because two things are fundamentally incompatible; effort spent pushing on it is wasted, and the only progress is to change what you're trying to do.

The distinction matters because the two look identical on a list of limitations, and they call for opposite responses. Most of ours are gaps. The two clearest cases, one of each, are worth taking first.

The unverified fields: a gap

Long-run parity with Godot is proven on 30 of the 77 state fields. Godot's save data covers 55 fields, so 22 fields can't be compared against Godot at all. The reason is mundane: Godot's state dump never writes them out.

That is a gap. Godot is open source, so its C++ can be extended to serialise every field. Once all 77 are visible to the oracle, the same gates and causal graph that already work on 30 fields enforce parity on all of them, and any drift they find is traceable by the same machinery. Nothing about the architecture changes; the work is instrumentation.

Scripts on the GPU: a wall

Of the 52 layout fields that no declared rule writes, 37 are written by game scripts. Those scripts run in Godot's scripting virtual machine, and no amount of money makes that VM run efficiently on a GPU.

This is the same argument as the engine-in-the-kernel essay. A GPU kernel is a flat function over arrays. A script runtime is pointer-chasing, dynamic dispatch and tagged unions. Those are incompatible execution models, not an unoptimised pairing.

The expensive non-answerYou could pay engineers to rewrite every dynamic system in a game (quests, UI, dialogue, enemy AI) by hand as flat arrays. That doesn't overcome the limit. It abandons Godot's scripting and builds a custom data-oriented engine inside the kernels, one game at a time.

Translate, don't port

The wall doesn't move, but the work of going around it can be automated. Most game logic follows a small number of predictable shapes, and each has a flat, fixed-size equivalent:

The plan is an AI-assisted transpiler that rewrites game scripts into the rule language. What makes that more than a code generator is the verification already in place. Because every rule is declared once and lowered three times, each translation can be run on the GPU and against the reference and checked by the parity gates. When the outputs diverge, the causal graph says which field diverged first, and the translator revises until parity passes.

The open question is how much real game logic fits these shapes. We won't know until we run it on real games, and we'll report the fraction that doesn't.

The other four

Collision events land one step late. The kernel records 74 contacts to Godot's 78 over 120 steps. This is structural, not a bug: the declared order makes contact detection read the previous step's transform, and declaring it same-step creates a cycle the order validator rejects. Splitting detection from resolution breaks the cycle. A gap.

The test scene is minimal. One physics body, a door and a trigger, and the kernel models one contact per world. The layout already reserves 64 contacts per world, so the next step is a multi-contact solver and a complete small Godot game ported through every gate. A gap.

There is no head-to-head benchmark. We have not measured Warp Core against many headless Godot instances on equal hardware, and rendering cost for watched lanes is unmeasured. Until that comparison exists we don't quote a speedup. A gap, and the most important one to close.

Four-card training scales poorly on this machine. On this machine's PCIe layout, data-parallel training reaches 0.77× scaling only with about sixteen micro-batches per collective, and below that four cards are a loss. This limits model training only: simulated worlds run independently and need no cross-card traffic. A hardware choice rather than a design limit.

The map

None of these blocks the architecture. They are where the work is. The last piece in this series, Simulation is priced per copy, is about what the architecture is for once they're closed.
