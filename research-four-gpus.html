Four GPUs, measured.
The topology is the ceiling.

Four consumer RDNA4 cards, measured from firmware up to training throughput. The links are fast, the settings barely matter, and two PCIe switches decide almost everything.

Adhitya Mohan 10 November 2026 Hardware ~8 min read

The headline number for this machine is easy to state: 5,052,188 world-steps per second at 4,096 parallel game worlds. The harder question is what the machine can do for the other half of the job, training models on what those worlds produce. That question is answered by the interconnect, and the interconnect is answered by working up from the firmware.

The machine

Four Radeon AI PRO R9700 cards, 32 GB each, on a Linux kernel built with peer-to-peer support, running ROCm 10.1. Every figure below was measured on it.

We report peak numbers, but each one comes with the condition behind it. FP8 matrix multiply reaches 239.05 TFLOP/s against 124.84 for bf16. Flash attention reaches 175.38 TFLOP/s. All-reduce reaches 20.6 GB/s against a 41.1 GB/s ceiling. The last number is the one that matters most, and the rest of this piece explains it.

The prerequisite chain

Peer-to-peer transfer between cards depends on a firmware setting before it depends on any software. The vendor's setup guide states that with Resize BAR disabled, peer-to-peer is turned off. On this machine the resize attribute is non-zero on all four cards and the first memory region maps the full 32 GB, so the setting is on. Above it sit the kernel options for peer-to-peer and peer DMA, both present, and then the collective library, which reports peer-to-peer on all twelve ordered pairs.

Why the order mattersA card with the firmware setting off still trains on one GPU. For every collective it silently falls back to copying through host memory, which looks exactly like a slow interconnect. You'd tune the wrong layer.

The ring ceiling

The links aren't the constraint. All four cards report a PCIe 5.0 ×16 link, and a raw peer copy runs at a uniform 27.40 GB/s on every ordered pair.

The topology is. Two PCIe switches carry two cards each. Every pair reports two hops, so traffic between switches crosses the CPU's root complex, and each switch's upstream link is shared by two cards.

A ring all-reduce over n ranks moves 2(n − 1)/n times the message across the fabric, so its bus bandwidth ceiling is that factor times the per-link rate:

2 × 3 / 4 = 1.5 → 1.5 × 27.40 GB/s = 41.1 GB/s

Measured all-reduce reaches 20.59 GB/s, or 50% of that ceiling.

Settings are not the lever

The natural response to 50% is to tune the collective library. We swept twelve configurations. The best moved the number by 1.6%.

FP8 and attention

FP8 works on this hardware. On a 4,096³ matrix multiply it's 1.91× bf16. The claim that it doesn't work, which appears in two library issue trackers, is about those libraries' architecture tables, not about the card.

The check is arithmetic. A 4,096³ multiply is 2 × 4,096³ ≈ 1.374 × 10¹¹ operations. At 124.84 TFLOP/s that's 1.10 ms, which matches the measured 1.101 ms. At 239.05 TFLOP/s it's 0.575 ms.

Shape matters. At 1,024³, FP8 gives no benefit at all, because that size is limited by kernel launch, not compute. At 8,192³ the ratio is 2.16, above the hardware's 2× dense rate, which means bf16 is underperforming there rather than FP8 beating its peak.

Flash attention runs through the composable-kernel path at 175.38 TFLOP/s for a 4,096-token sequence, 33.5× the fallback (1.567 ms against 52.507 ms). The guards that gate this path list the datacenter parts, not because the consumer part can't run the kernel, but because the datacenter path behaves differently.

What four cards deliver

Take flash attention as the workload and a 151-million-parameter model, so the bf16 gradient is 302 MB, with one all-reduce per step. Four cards are slower than one. The all-reduce takes 22.79 ms and the compute takes 4.4 ms, so the step is almost all communication and the scaling is 0.19.

That number is predictable from first principles:

1.5 × 3.02×10⁸ B / 20.6×10⁹ B/s ≈ 0.022 s (measured: 22.79 ms)

Gradient accumulation fixes the ratio, because compute scales with the number of micro-batches and the collective doesn't:

A two-parameter model explains the column. With A micro-batches, compute k per micro-batch and collective time c, the collective share is c / (A·k + c). At A = 1 the measured 83.7% gives c = 5.14k. That predicts 24.3% at A = 16; the measurement is 22.7%, within 1.6 points.

A larger model doesn't help, because it raises compute and gradient together. At a model width of 4,096 the gradient is 4.8 GB and the collective takes 361 ms, which swamps any attention compute at these sequence lengths. At 7 billion parameters the gradient is 14 GB and one collective costs about a second.

The conclusion: on this box, data parallelism needs about sixteen micro-batches per collective to reach 0.77 scaling, and below that it's a loss. No collective setting changes that. A different topology would.

The stack matters more than the flags

One last trap. The machine's system Python carries a PyTorch built against one ROCm version while the installed toolkit is another. The matching stack is a container image with PyTorch 2.13 built against ROCm 10.1. Measuring on the system interpreter gives numbers that look plausible and belong to a different software stack.
