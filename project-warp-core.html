Warp Core.
Thousands of worlds, one GPU.

Warp Core runs a Godot game's rules and physics as GPU kernels, one complete copy of the game per GPU lane, thousands of lanes at once. Godot stops being the bottleneck and becomes the window you watch any one copy through. Built in is the proof the copies are real: one set of rules, three backends that must agree, and a trace from any fault back to where it began.

01 / What it isThe engine is the window

Run the game
a thousand times.

Testing a game is limited by how many play sessions you can afford. A human plays one. A scripted bot needs a whole engine instance per session, with all of its memory and CPU cost.

Warp Core changes the unit of cost. Each copy holds only the state that changes, about 10 KB per world. Meshes, textures and level geometry are stored once and shared, so 4,096 worlds fit in about 41 MB. We first proved the idea by running a whole commercial console game as GPU kernels; Warp Core brings it to a modern, open engine.

Parallel worlds

Thousands of independent copies of the same scene step together. Each can take different inputs and branch from any saved state.

Shared assets

Cost scales with game state, not with the engine. Adding a world means adding a save file, not another engine.

Godot in the loop

A Godot save can be loaded into a GPU lane and resumed, and any lane can be watched live in Godot. Developers keep their engine and workflow.

Fixed state layout

A 77-field game state in 13 blocks (transforms, bodies, camera, input, contacts and more), generated from one specification.

Proven today

  • 5,052,188 world-steps per second at 4,096 worlds on four consumer AMD GPUs.
  • Bit-identical to Godot over 23,820 steps and 144 restarts, on 30 of the 77 state fields.
  • A Godot save resumed on the GPU is exact at the moment of resume, and within 0.006 afterward.
  • Every one of 4,096 worlds matches a single-world run.
  • 10 of 10 injected bug classes traced to the correct variable, and GPU, NumPy and GDScript backends bit-identical on the tested rules.
  • About 1 µs to publish a frame to Godot and 0.8 µs to read one, with zero torn frames in 10,000 reads against a live writer.

Not yet proven

  • Throughput on a real game with many objects. The kernel models one contact at a time today.
  • Game scripts don't run on the GPU. Script variables must be declared as simulation state; 37 of 77 fields are still written by scripts.
  • Collision events land one step late (74 contacts against Godot's 78 over 120 steps).
  • Fault tracing is shown on bugs we inject. Finding real, unseeded bugs in a partner's game is the next test.
  • Rules are compiled, game scripts are not: they must be declared as simulation state to take part. Godot's own save data covers 55 fields, so 22 can't be compared yet.
  • No head-to-head benchmark yet against many headless Godot instances on the same hardware.
03 / DemoA ball, a door, 4,096 worlds

Godot is
just the TV.

In the demo, the GPU steps 4,096 copies of a small scene at once. Godot reads one of them through shared memory and draws it. It doesn't simulate anything: stop the GPU and the window freezes.

Think of 4,096 consoles sharing one cartridge, each with its own save file. Godot is the TV plugged into console zero. We run the demo live on calls with design partners and investors.

04 / VerificationProof the copies are real

Same rules,
three calculators.

Thousands of GPU copies of a game are only useful if they behave like the game. Anyone can make a fast demo; the hard part is knowing the fast copy hasn't quietly drifted from the real one. Warp Core answers that by construction: every rule is written once and compiled three ways, and the three must give the same answer.

Because every rule declares what it reads and writes, Warp Core also knows how the game's state depends on itself. When a world goes wrong, that dependency graph leads back to the variable where the fault started. Two independent adversarial audits rejected an early sign-off; every finding was fixed or explicitly scoped out.

Declare once

A rule states what it reads, what it writes and its logic. It compiles to GPU kernels, to NumPy as a reference, and to GDScript to run inside Godot. All three are bit-identical on the tested rules.

Derived scheduling

Rule order, per-step change tracking and the causal graph are calculated from the declarations, not maintained by hand. Switching over found three real dependency errors in the hand-written tables.

Fault-tracing gates

Automated tests inject known classes of game bug, such as update-order errors, collision gaps, timer overflow and precision loss, and check each is traced to the right variable.

Live transport

A Godot extension reads GPU state through lock-free shared memory. A step is only visible once it's complete, so Godot never draws a half-written frame.

Break it on purpose

One command runs every gate: the three backends are compared step by step, then planted bugs (a bounce that's too bouncy, a door that never opens) are injected and the harness has to name the exact wrong variable. It writes a pass/fail report. A second command opens the live Godot viewer on the same simulation.

# run every gate, write a pass/fail report
python -m conduit.cli gates

Run by us during pilots and live demos. The harness isn't publicly released; it's included in every pilot, and access for your own simulation is available by request.

05 / UsageWhat a pilot looks like

From your scene
to a findings report.

Today Warp Core is used hands-on, with us. You keep your game in Godot; we do the porting and run the worlds. Automated bug-hunting agents that explore the lanes on their own are in development and will join pilots as they're ready.

  1. Scope

    Pick a scene or subsystem where bugs are rare, costly or hard to reproduce: physics, collisions, timers, doors and triggers.

  2. Declare state & port rules

    We declare the scene's changing state and move its rules onto the GPU. Script variables that matter are declared as simulation state.

  3. Gate it

    Warp Core's gates check the GPU copies against Godot itself before any result counts.

  4. Run thousands of worlds

    Varied inputs, branches from saved states, and faults injected on purpose, all in parallel.

  5. Deliver findings

    Each finding comes with a fault trace to the variable where it began, a state snapshot to load in Godot, and a replay.

07 / What's nextPrototype → pilot

Closing the
known gaps.

  1. Benchmark against the baseline

    Warp Core against many headless Godot instances on equal hardware, with a published cost per million game-steps.

  2. A real game

    A small but complete Godot game with multiple bodies, multi-contact collisions and declared script state, re-run through every gate.

  3. Close the gaps

    Fix collision timing and extend checked coverage beyond 30 of the 77 fields.

  4. Plugin & CI

    A Godot plugin and CI step that run the verification gates on every build and flag regressions with a trace. Join the list.

  5. An exploration agent

    Search and reinforcement learning across the parallel lanes, finding seeded and real bugs on its own.
