Boulder Research / Research / Simulation architecture

Simulation is priced per copy.
Change the unit.

Running a world a thousand times usually means running an engine a thousand times. When the unit of cost becomes the state that changes, three kinds of work get cheaper, and the engine stops being the thing that matters.

The other essays in this series are about whether the architecture works: where the split goes, how we check it, what the hardware gives, what's still missing. This one is about why it's worth building.

The unit of cost

Today, a thousand copies of a world means a thousand engine instances, each with its full memory footprint and its own CPU time. The cost scales with the engine, and most of the engine is the same in every copy.

In Warp Core the cost scales with what changes. The immutable tier (meshes, textures, level geometry) is stored once. Each extra world adds its mutable state, about 10 KB in the current layout, so 4,096 worlds fit in about 41 MB. The arithmetic is in the first essay.

A world model learns from the worlds you can afford to run. The point is to make running them cheap.

Three things follow from changing the unit.

Search at scale

Thousands of worlds can branch from the same saved state and try different actions. That's the exploration that reinforcement learning, Go-Explore-style search and automated game testing all depend on, and it's the source of the counterfactual data described in Four open problems. Lane independence is already checked: each of 4,096 lanes matches a single-lane run over 8 ticks.

Faults with a diagnosis

Because the causal graph is derived from the rules, a world that goes wrong comes with a trace back to the field where it started. In testing terms, a failure arrives with its cause rather than as a video someone has to watch. The ten mutation gates are the evidence that the trace points to the right place.

Ground truth for learned models

Every world produces exact, labelled state at every step. That's training data for world models, and it's also an oracle to check their predictions against, so they can be re-anchored before they drift into plausible fiction. This is the "state that can be read and drawn" from the open problems, supplied by an engine rather than inferred from pixels.

Nothing here is specific to Godot

A game engine is a world simulator with a renderer. Godot happens to be open source, modifiable at any depth and free to deploy, which is why we started there, and why teams outside games already use it for interactive 3D simulation.

But the core pieces describe any world that steps forward in time:

  • the state contract, which fixes what a world is in memory;
  • the rule language, which declares each rule once;
  • the compiler, which lowers rules to parallel GPU lanes and to reference backends;
  • the parity gates, which check the lanes against the source;
  • the causal graph, which traces a fault to where it started.

Adding another source (another engine, a robotics simulator such as MuJoCo, an industrial process model) means adding a front end that reads its logic and an oracle that checks against it. The verified core in the middle stays the same.

StatusGodot is the only source built today. Every other source in this section is an expansion path, and none has been attempted.

What compounds

If the core holds, three things get cheaper over time rather than more expensive:

  • Each source is cheaper than the last. The core and its gates are reused; a new source adds a front end and an oracle, not a new system.
  • Translation improves with use. If script translation works as planned (see Translate, don't port), every verified translation becomes an example for the next.
  • The data accumulates. Exact action, state and failure trajectories are scarce. Every world run produces more of them.
Start with games, because they reset. End with any world that steps forward in time.
